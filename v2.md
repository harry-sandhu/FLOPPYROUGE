# FloppyRogue — Design Specification v2
(Player rework, Items, Rooms/Dungeon, Enemies, Bosses)

## 1. Player System

### 1.1 Base stats (all modifiable by items)

damage — per-projectile damage, base 10
shotSpeed — pixels/sec, base 140
range — max travel distance before despawn, base ~150px
fireRate — shots per second, base 3.0 (hold-to-fire)
projectileCount — projectiles per shot, base 1
moveSpeed — base 60
maxHp — base 100


### 1.2 Shooting behavior
- **Base kit:** 4 cardinal directions only (Up/Down/Left/Right arrows).
- **Hold-to-fire:** holding a direction fires repeatedly at `1 / fireRate` seconds between shots, not one-shot-per-press.
- **Two arrows pressed simultaneously (base kit):** cancels, no shot — unless the diagonal-fire item is owned.
- **Diagonal fire (item unlock):** if owned, two simultaneously-held arrows fire in the combined diagonal direction (Up+Left → fires up-left) instead of canceling.

### 1.3 Dash (item unlock)
- Bound to Space. Does nothing if the item isn't owned.
- With the item: Space triggers a short burst of movement in the player's current facing/move direction, with brief invincibility frames during the dash (reuses the existing `invincibleTimer` mechanism on `Player`).
- Stats to add: `dashSpeed`, `dashDuration`, `dashCooldown`.

### 1.4 Required structural changes
- `Player` struct gains the full stat block above plus two bool flags: `hasDiagonalFire`, `hasDash`.
- Shooting logic moves from raw arrow-key checks in `main.cpp` into a `PlayerLogic::HandleShooting(...)` function that:
  1. Reads held arrow keys.
  2. Determines fire direction (cardinal or diagonal depending on `hasDiagonalFire` and key combo).
  3. Applies a fire-rate cooldown timer (new field on `Player`: `fireCooldownRemaining`).
  4. Spawns `projectileCount` projectiles per shot (initially just 1; multi-shot items add spread later) using `damage`/`shotSpeed`/`range` from player stats, not hardcoded constants.
- `Projectile` gains `damage` and `remainingRange` (or spawn pos + max distance check) so per-shot damage/range reflect the player's current stats at time of firing.

## 2. Item System

### 2.1 Item categories
- **Stat modifiers** — flat or percentage changes to one or more player stats (damage, fireRate, moveSpeed, range, projectileCount, maxHp).
- **Unlock flags** — one-time behavioral unlocks: `diagonal_fire`, `dash`.
- **(Future)** on-hit/on-kill/on-shoot hooks (freeze, poison, ricochet, pierce) — not needed for the first item pass, but the effect struct should be designed so these can be added without restructuring later.

### 2.2 Data-driven design
Items live in `data/items.txt`, same key=value block format as enemies:

[DamageUp]
type=stat_mod
stat=damage
mode=add
value=5

[FireRateUp]
type=stat_mod
stat=fireRate
mode=multiply
value=1.2

[DiagonalFire]
type=unlock
flag=diagonal_fire

[Dash]
type=unlock
flag=dash

- `mode=add` — flat addition to the stat.
- `mode=multiply` — percentage-style scaling.
- `type=unlock` — sets a bool flag on `Player` instead of touching a numeric stat.

### 2.3 Application
- `ItemSystem::ApplyItem(Player& player, const ItemTemplate& item)` — reads `type`, branches to either stat-mod application or flag-set.
- Items are permanent for the run once picked up (no removal system needed initially).
- Player needs an `std::vector`-free fixed-size list of owned item IDs if you want to display an inventory later — not required for v1, but worth reserving a `ownedItemCount` + fixed array now so the struct doesn't need reshaping later.

## 3. Enemy System (expansion, not new architecture)

- Add more `[EnemyName]` blocks to `data/enemies.txt` — pure content work, no code changes needed beyond what already exists.
- Add stat variety within existing AI types (e.g. `FireZombie`: `ai=CHASER`, higher hp/speed than `Zombie`) to prove the "same code, different numbers" pattern.
- **Spawn randomization:** instead of `main.cpp` hardcoding `Spawn("Zombie", ...)` / `Spawn("Gunner", ...)`, a `Room` (once it exists — see §5) holds a small pool of eligible enemy names + a spawn-point list, and picks N enemies at random using the seeded RNG when the room is entered.
- **CHARGER / SUMMONER / EXPLODER** — each needs one new `Update*` function in `enemy.cpp` plus a `case` in the dispatch switch, same pattern as CHASER/SHOOTER. No new files needed, just extending `enemy.cpp`.

---

## 4. Boss System (expansion, not new architecture)

- 2 more bosses, each as a new set of attack-pattern functions (following the `boss.cpp` pattern: `FireX`, `FireY`, phase-based cooldown).
- Recommend moving boss selection to data eventually (`data/bosses.txt` with a name + which attack-pattern set to use), but this can wait — hardcoded `SpawnBoss1()`, `SpawnBoss2()`, `SpawnBoss3()` functions are fine short-term, since only 3 total exist.
- Each boss should get a distinct visual color (already the pattern) and a distinct attack rhythm so they feel different even as flat-colored squares.

## 5. Room & Dungeon System

This is the biggest new piece. Breaking it into: room types, room data structure, floor layout generation, and transition/gating logic.

### 5.1 Room types
```cpp
enum class RoomType {
    START,
    NORMAL,
    BOSS,
    TREASURE,
    CURSE
    // more types can be added later — this enum is designed to extend
};
```

| Type | Contents | Entry effect | Exit effect | Gate behavior |
|---|---|---|---|---|
| START | Nothing — just the player | none | none | Always exactly 1 per floor. Gate open immediately. |
| NORMAL | Randomized enemy pool | none | none | Gate locked until all enemies cleared, then opens. |
| BOSS | The boss for this floor | none | none | Gate locked until boss dies. Clearing it opens the way to the next floor. |
| TREASURE | Item pickup(s), no enemies | none | none | Gate always open — no combat gating. |
| CURSE | Items or enemies | player takes HP damage on entry | player takes HP damage on exit | Gate always open, but cost is paid both ways. |

### 5.2 Room struct (extends the existing `Room` bounding-box struct)
```cpp
struct Room {
    RoomType type = RoomType::NORMAL;
    Rect bounds;                    // existing ClampToRoom logic still applies
    Vec2 gridPos;                   // position in the floor's room graph, e.g. (2,1)

    bool cleared = false;           // for NORMAL/BOSS: enemies/boss dead
    bool gateOpen = false;

    // Connections to neighboring rooms — index into the floor's room list,
    // or -1 if no connection in that direction.
    int north = -1, south = -1, east = -1, west = -1;

    // Content, populated at generation time:
    std::vector<int> enemySpawnList;   // indices/names into enemy pool, NORMAL rooms
    // boss rooms reference a boss id/index instead
    // treasure/curse rooms reference item pool entries
};
```

### 5.3 Floor generation algorithm
Given the placement rules you specified:
- Start room: **farthest from boss room**.
- Treasure room: **prefers close to start, far from boss**.
- Curse room: **anywhere except adjacent to boss room**.
- Remaining rooms: **normal rooms** (enemy encounters), filling out the rest of the floor.

**Recommended approach — grid-based graph, generated like this:**

1. **Pick a grid size** (e.g. 5x5 or 6x6 conceptual grid — not all cells used).
2. **Place the boss room** first, at a random cell (or a random edge cell, which tends to produce better dungeon shapes).
3. **Run a BFS/distance calculation** from the boss room across the grid (graph distance, i.e. number of room-hops, not Euclidean distance) to get a "distance from boss" value for every cell.
4. **Place the start room** at the cell with **maximum distance from boss** among cells that will be used. (If multiple cells tie for max distance, pick randomly among them.)
5. **Generate the connecting path/tree** between start and boss first — this guarantees the floor is always completable. A random walk or simple randomized BFS spanning tree works well here.
6. **Place the treasure room**: among remaining unused-but-reachable cells, filter to ones with **low distance from start** and **high distance from boss**, then pick randomly among the best-scoring candidates (e.g. score = distanceFromStart\*(-1) + distanceFromBoss, pick lowest/best).
7. **Place the curse room**: among remaining cells, filter out any cell **adjacent to the boss room** (distance 1 from boss), then pick randomly from what's left.
8. **Fill all remaining connected cells with NORMAL rooms.**
9. **Build gate connections** (`north`/`south`/`east`/`west`) based on which adjacent cells are actually part of the generated layout.

This satisfies every rule you gave, is fully data-driven (grid size, room counts could later move to `data/rooms.txt` as generation parameters), and reuses the RNG module already planned in `engine/core/rng.h`.

### 5.4 Transition logic
- `Dungeon` (new module, `game/dungeon/dungeon.h/.cpp`) holds the generated room list + current room index.
- Player reaching a gate edge while `gateOpen == true` triggers `Dungeon::TransitionTo(direction)`, which:
  - Swaps the active room.
  - Repositions the player at the corresponding entry point of the new room (opposite side from the gate they exited through).
  - Triggers room-entry effects (spawn enemies for NORMAL, apply curse-room entry damage, etc.).
- `main.cpp`'s big state machine (`PLAYING` / `BOSS_FIGHT` / `WON` / `LOST`) gets restructured to track **current room type + cleared state** instead of two hardcoded states — this is a real refactor, not just an addition, since right now the game assumes exactly one normal-room phase then one boss phase.

### 5.5 Minimum viable version (don't over-scope this first pass)
Given time constraints, the first working version doesn't need full multi-floor progression — just:
- One floor.
- Grid-generated rooms following the placement rules above.
- Start → (some path of normal rooms) → boss room, with treasure/curse rooms reachable but optional (player doesn't have to visit them to reach the boss).
- "Next floor" can literally just regenerate a new floor and reset the player position — full progression/scoring across floors is a later refinement, not required for the core loop to work.

## 6. Suggested build order (given everything above)

1. **Player rework** — stat block, hold-to-fire, cardinal-only shooting reading from stats instead of hardcoded values. (Diagonal fire / dash code paths can be written now but gated behind flags that default false — no items needed yet to build this part.)
2. **Item system** — data file, parser reuse, `ApplyItem`, the two unlock items (diagonal fire, dash) plus 3-4 stat-mod items to start.
3. **Room/dungeon system** — this is the big one per §5. Build the grid generation + room struct + transition logic. Start with the minimum viable version in §5.5.
4. **Wire enemies into NORMAL rooms** — spawn pool + randomized selection per room, replacing the hardcoded 2-enemy setup.
5. **Wire treasure/curse rooms to the item system** — treasure room drops N items on entry; curse room applies entry/exit HP cost and optionally spawns enemies or items too.
6. **Content pass** — more enemies (variety + remaining AI types), 2 more bosses, more items.
7. **Polish pass** — juice, audio, sprites (already on the earlier roadmap, unchanged).

Each step only depends on the ones before it, so this order avoids building anything with nowhere to plug into yet.
